# JD 标注口径

本文说明 `data/jds/*.json` 里 `annotations` 字段的口径。
**每份 JD 的 JSON 里也抄了同一份**（`annotations.rubric`），这样单独打开一个文件
也能看懂它的标注是怎么来的。

---

## 1. 什么算「一条要求」

**算**：JD 里明确写出的「技能 / 技术 / 工具 / 方法 / 能力」，
并且是**这个岗位要招人具备**的东西。

例子（来自 `2008789833664847872`）：
- ✅「熟悉 Spring Boot、Spring Cloud、MySQL、Redis、消息队列等常用技术」→ 拆成 5 条
- ✅「熟练掌握 Python、Go 或 C++ 中至少一种语言」→ 拆成 3 条
- ✅「了解大模型应用开发」→ 1 条

**不算**（排除项）：
- ❌ 学历与年限要求：「本科及以上学历」「3 年以上工作经验」
- ❌ 软素质：「良好的沟通协作能力」「抗压能力强」「有责任心」
- ❌ 纯业务描述：「负责电商核心系统的需求分析、方案设计」
- ❌ 薪酬福利、团队规模、签约主体
- ❌ 会议与期刊名（会被当作技能抽出来，但它们不是技能要求）

---

## 2. 重要度判定

| 重要度 | 判据 |
|--------|------|
| **必须** | 原文出现 精通 / 熟练掌握 / 扎实 / 深入理解 / 具备…经验 / 至少… 等硬性表述，**或**写在任职要求里的无条件句 |
| **加分** | 原文出现 优先 / 加分 / 更佳 / 有兴趣 / …者优先 |

**边界案例的统一处理**：「熟悉 X，有 Y 经验者优先」→ 判 **必须**
（硬性条件在前，「优先」是附加条件）。

> 这条规则写死在这里，是因为它必须**统一**：同一个 JD 里如果一会儿这么判、
> 一会儿那么判，重要度加权指标就失去意义了。

---

## 3. 技能名归一化

标注时写的技能名要能用 `jobfit.normalize` 归一化到**词表规范名**
（`jobfit/lexicon.py`）。这一步是为了让三方对齐到同一个集合：

- LLM 抽出来的（可能写「SFT」）
- 规则抽出来的（词表里的「LLM微调」）
- 人工标注的（写「LLM微调」）

归一化做两件事：
1. **别名映射**：`SFT` → `LLM微调`，`RLVR` → `DPO`，`SpringBoot` → `Spring Boot`；
2. **复合短语拆分**：「高并发、高可靠海量服务开发」按强分隔符（顿号/逗号/分号/斜杠）拆开；
   弱分隔符（和/与/及）只有当**每一段都查得到**时才拆（避免把「零售与批发」这种拆坏）。

标注时如果某个技能**词表里查不到**，就写原文（如「大模型应用落地」），
它会以「词表外技能」参与评测。

---

## 4. 原文证据

每条标注必须带一段 **JD 原文的逐字片段**。

- 写的是**短片段**（如「熟悉 Spring Boot、Spring Cloud、MySQL」），不是整句；
- `scripts/build_dataset.py` 会在原文里定位它，并**扩展成完整句子**存进 JSON；
- 定位不到 → **直接报错**。

> 为什么这么严：标注与原文脱节是**静默失效**——文件看起来正常，
> 但指标算的是另一套东西。必须让它炸出来。

---

## 5. 「期望推荐哪版简历」标签

`data/jds/*.json` 的 `expected_resume` 字段标的是**岗位族**：

| 岗位族 | 对应简历 |
|--------|----------|
| `ai_engineering` | 简历202607-AI工程 |
| `java_backend` | 简历202607-Java开发 |
| `nlp_algorithm` | 简历202607-NLP算法 |
| `eval_posttrain` | 简历202607-评测后训练-有联 |

**标注依据**：JD 的核心职责与主要技术栈落在哪个岗位族的主线上。

> 试过用「人工标注真值表里覆盖必须项最多的那份简历」来客观推导，
> 但**退化了**——评测后训练版简历覆盖的技能最多，于是几乎每份 JD 都推导出它，
> 指标变成「总选覆盖面最广的那份」，测不出岗位匹配能力。
> 所以改回人工标签（也符合规格「给出该岗位族标注的期望版本」）。
> 这次失败写在 `scripts/run_eval.py` 的注释里。

---

## 6. 已知偏差

1. **单人标注**，没有第二标注者做交叉复核。
2. 「什么算一条要求」有主观性——比如「AI 辅助开发」算不算技能要求，
   本项目按「算」处理（它是一个具体的工作方式，不只是软素质）。
3. 重要度边界案例按第 2 节的规则统一判定，但规则本身是人定的。
4. 自写变体（3 份）的标注由同一人完成，与真实 JD 的标注不构成独立复核。

这些都写进 `experiments/results/eval_results.json` 的 `caveats` 段，
README 的「诚实边界」一节也引用了它们。
